# Native Windows check broker: implemented stage and qualification gaps

## Scope and current decision

Issue [#8](https://github.com/paulgreenbox-beep/makepad-sandstudio/issues/8) is continued in existing Draft [PR #9](https://github.com/paulgreenbox-beep/makepad-sandstudio/pull/9), based on dispatcher PR #7. This stage adds strict protocol binding and real Windows supervisor probes. It does not qualify execution of repository or agent-generated code. The production binary remains fail-closed and the Codex Issue dispatcher remains disabled.

`src/main.rs` accepts no command-line arguments, reads at most 64 KiB from stdin, and emits only fixed refusal codes on stderr. Its stdout remains empty and it never produces a check receipt or `PASS`. A valid request still exits with `BLOCKED` because controller authority, protected source import, execution identity/profile, broad filesystem restrictions, network restrictions and authenticated evidence/receipts have not been qualified. The opt-in `native-probes` code is a separate library/test path for owner-controlled fixture images; it is not a production authorization mechanism.

## Protocol and trust model

The wire formats remain `mss-native-check-request-v1` and `mss-check-receipt-v1`. Input is deserialized directly into strict typed structures, so duplicate recognized keys and unknown fields are rejected at request/check level. Typed catalog, manifest and GOAL readers apply the same rule; converting through a generic JSON map first would lose that duplicate-key protection and must not be used.

The request requires canonical positive decimal run ID spelling, a nonzero 40-character lowercase source SHA, one canonical `MSS-XXX` ID, and a lexically full Windows drive path. Relative paths, device/UNC spellings, traversal, alternate streams, reserved names and trailing-dot/space aliases are rejected. These are lexical checks, not filesystem canonicalization, a reparse proof or caller authentication.

`bind_request` compares the request to an independently obtained protected execution binding, the existing manifest/GOAL document, exact check metadata and literal argv in the approved scope/catalog. It requires the selected GOAL to be `IN_PROGRESS` with the expected branch and owner. It does not create a new task registry or weaken required checks. The real catalog IDs `CORE_TEST` and `WORKSPACE_CHECK` are used; invented aliases are not accepted as equivalents. Selected `command:null` entries such as `WINDOWS_DESKTOP` and `TOOLKIT_PARITY` are blocked as manual obligations.

The public binding API does not authenticate whoever constructs its expected context. Copying stdin into an `ExecutionBinding` would prove nothing. Production still needs a protected launch authority that binds caller identity, GOAL, attempt, source, repository object store, permitted commands and ownership generation. The stdin protocol itself contains no caller credential or authenticated session nonce.

## Native probe supervisor

The feature-gated supervisor constructs a restricted version of its own token with disabled maximum privileges, a deny-only Administrators SID, restricting SIDs and low integrity. It queries token groups, elevation, integrity and enabled privileges. The intended child must be suspended while the supervisor reads its actual token and verifies Job membership and Win32k mitigation before resuming it. This uses [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) and [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw). Neither the token-creation flags nor `IsTokenRestricted` alone establish complete isolation.

The RC, World and Builtin Users restricting SIDs are common identities. They are retained, with an additional fresh nonce restricting SID for each probe Run. The nonce is an object-access marker, not a separately authenticated Windows account or full session security principal. The ACL probes deliberately control their synthetic object descriptors; passing those tests does not establish isolation between arbitrary same-user sessions, profiles, credentials or processes.

The restricted token copy's DefaultDacl preserves its existing ACEs and adds an allow ACE for that Run's nonce SID. This permits access to its own subsequently created kernel objects, whose access checks also evaluate restricting SIDs. It does not edit the source token or an existing host-object ACL, add the logon SID to the restricting list, or relax privilege/integrity restrictions. The native regression observes unchanged source-token ACEs, all original copy ACEs and RC/World/Users restrictions, and exactly one additional nonce ACE/SID. Successful real child startup is the runtime proof; no separate default-security event probe was executed. This resolves the observed pre-main `STATUS_DLL_INIT_FAILED` (`0xC0000142`) without weakening the token or Win32k policy.

The image is opened without write/delete sharing, hashed, and identified by its file identity. Non-reparse ancestor handles are retained without delete sharing through launch. This prevents replacement of a pinned fixture file/object within the tested handle lifetime; it is not an immutable repository checkout or an audit of every loaded DLL.

Process construction uses an explicit executable path and separately quoted argument vector without a shell. `PROC_THREAD_ATTRIBUTE_JOB_LIST` associates the new process with its owned Job at creation, while `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` admits only null stdin and the selected output pipe handles. The Job handle is not a general inherited capability. `DETACHED_PROCESS` prevents allocation of a console host while preserving those explicit standard handles; the earlier `CREATE_NO_WINDOW` path could leave an owned console host in the Job. The implementation requests Win32k system-call disable mitigation and checks the actual child policy. See Microsoft's [process attribute documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

The trusted supervisor fixture and restricted child fixture are separate binaries. The child does not directly import USER32, GDI32 or WIN32U; it reports startup settings and mitigation using non-UI APIs. This split avoids requiring the locked-down child to load the supervisor's desktop-management code. It is not a complete audit of all transitively loaded or externally injected modules.

The Job is configured for kill-on-close, at most four active processes, 128 MiB per-process memory, 256 MiB total Job memory and a 10% CPU hard cap. No breakaway flag is permitted. The implementation records PID and process birth time and uses retained handles for its own process tree. A Job configuration query proves the kernel object contains those limits; separate child probes now observe descendant membership, timeout/cancellation and process-tree cleanup. They do not prove resource-exhaustion behavior or every possible escape. The post-exit process-ID query distinguishes a briefly accounted primary from remaining descendants. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describe lifetime/accounting controls; [Job security](https://learn.microsoft.com/en-us/windows/win32/procthread/job-object-security-and-access-rights) does not replace per-process security.

Cleanup now retains read/query-and-synchronize handles for enumerated Job members and verifies each handle is still a member of the exact owned Job before using it. Those enumerated PIDs are never mutation targets. After any required owned-Job termination, the primary and retained member handles must all signal within one shared three-second deadline, followed by zero active Job processes within that same deadline. The descendant test requires at least two waited handles, covering both primary and its held-live descendant. A termination acknowledgement or accounting zero alone is insufficient. An uncertain termination API result is fenced before return so `Drop` does not replay that request. Enumeration is a bounded snapshot; races involving arbitrary new descendant creation and exhaustive OS isolation remain `NOT_VERIFIED`.

Each Run creates its own uniquely named private desktop in the controller's existing, unchanged window station. This is **not a separate noninteractive window station**; station-wide clipboard/atom and hostile same-user boundaries are not qualified. The old create-only station design failed with error 183 because Windows derives an existing station name from the logon session for a nonadministrator. The replacement never creates, selects or reconfigures a window station. It never opens the user's Default desktop, calls `SetProcessWindowStation`, `SetThreadDesktop` or `SwitchDesktop`, or sends desktop input. See [CreateWindowStationW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createwindowstationw) and [Window Stations](https://learn.microsoft.com/en-us/windows/win32/winstation/window-stations).

The desktop descriptor grants only the controller user and the independent per-Run nonce SID full desktop access (`0xf01ff`), as required by the `CreateProcessAsUserW` startup contract. This grant applies only to the fresh owned desktop. Its protected owner/DACL and low integrity label are read back exactly; the OS-serialized owner/DACL/label SDDL SHA-256 is pinned at creation and rechecked with parent context. `UOI_IO` must be false. Existing-name collisions are refused without changing the found object, and the nonce descriptor is independently checked after creation to reject a race. The creating helper thread exits before the controller can close the desktop. Parent desktop identity and window-station owner/DACL snapshots must remain unchanged. On a completed normal, timeout or cancellation observation, checked close and a failed reopen with `ERROR_FILE_NOT_FOUND` confirm owned-desktop cleanup.

The child reports its exact startup `lpDesktop` and observed Win32k-disable policy; the supervisor also verifies mitigation before resuming the suspended child. The follow-up waits for an actual child READY report, limited to an eight-KiB first line and a maximum five-second wait, and checks PID/TID, Job/token facts, startup desktop and Win32k policy. The primary thread handle is retained. Process/thread liveness, thread ownership, Win32k mitigation and parent context are checked before and after querying that running thread. A successful `GetThreadDesktop` result must match the owned name, pinned creation descriptor hash and noninput state.

The running-thread USER32 query occurs only inside the disposable supervisor that the crash test will terminate. Its returned handle is borrowed and is never explicitly closed; keeping such an observation in a long-lived test parent could contaminate the desktop-lifetime proof. The pre-resume NULL query remains recorded in `child_connected_desktop` / `child_desktop_query_win32`. The new post-READY result is independently typed as `OBSERVED` or `QUERY_UNAVAILABLE`. In the tested run it was still NULL with the cleared/read-back error zero: `MSS_USER32_QUERY status=QUERY_UNAVAILABLE win32=0 association_required_result=BLOCKED`. `require_observed` refuses that result. NULL is neither proof of no connection nor proof of assigned desktop. Actual USER32 association remains `NOT_VERIFIED`, with its required-association gate `BLOCKED`; successful test coverage of this refusal is not association PASS. No GUI connection is forced and mitigation is not relaxed. See [GetThreadDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getthreaddesktop).

Stdout and stderr are drained concurrently and retained up to 64 KiB each; overflow or read failure marks output incomplete. The bounded READY channel does not replace these complete-stream gates. Timeout/cancellation paths target only the owned Job and require the process-handle termination barrier and accounting before reporting cleanup. The real child probes observe these paths, including survival of a simultaneous distinct owned Job. An incomplete stream, uncertain termination or remaining child cannot be normalized to successful check acceptance.

The crash test first observes the exact private desktop within its unchanged current station, checks its pinned owner/DACL/label SDDL hash and `UOI_IO=false`, and retains an explicit noninherited observer witness. The ready child has a fixed twenty-second hold independent of supervisor EOF. Immediately before killing only the retained owned supervisor, the child is alive and total test time is below ten seconds; both supervisor and PID/birth/image-verified child must then terminate within their respective five-second waits, and child death must occur before the twenty-second natural exit. The witness is verified again and explicitly closed after those deaths. `OpenDesktopW` is then polled for at most three seconds using documented query rights, closing every successful transient handle. Only NULL with `ERROR_FILE_NOT_FOUND` (2) proves absence; access denial is not absence. The source-bound observed marker is `MSS_CRASH_DESKTOP before_exists=true after_absent=true`. This proves disappearance of the owned desktop after supervisor/child death **and observer release**, not instantaneous destruction while an observer still holds it. It does not qualify arbitrary crash recovery, future hostile workloads or full OS isolation.

## Source, replay and receipt work still required

The dispatcher invokes the broker before pushing the newly committed source. A normal protected remote mirror does not yet contain that commit. Production needs an authenticated, bounded object import into a protected store and then a broker-owned clean materializer that verifies the commit, trusted repository identity, tree/object integrity and resulting files. It must not execute Git using an agent-controlled `.git` configuration, hooks, filters, alternates or URL, copy untracked/ignored files, or reuse an agent-modified `target` directory.

The materialized tree must be protected against changes throughout checks, and each allowed logical tool name must resolve to a reviewed fixed executable identity. Its own controlled runtime/DLL dependencies require qualification. A later source mutation invalidates applicability of old receipts rather than changing or deleting historical evidence.

A persistent create-new attempt-fence primitive exists, but it is not connected to production execution. Its caller must supply a controller-owned private root; creating a file does not establish that root's authority. The production journal still needs authenticated GOAL/run/source binding, protection against concurrent callers, crash/recovery policy and explicit unknown outcomes. Stdin field shape is not freshness proof. The full control/worker identity handoff must be authenticated before any check is resumed; caller-provided paths and IDs cannot become authority by comparison to copies of themselves.

Only a qualified executor may produce `mss-check-receipt-v1`. Receipts must preserve exact GOAL/run/source/check/argv, runner identity, times, exit/result and verifiable evidence digests. `CORE_TEST` also requires the catalog's real test summary. The production broker must distinguish failed start, timeout, cancellation, truncated output, uncertain cleanup and unknown termination. It must not replay a potentially mutating check after an uncertain result.

Raw potential secrets, absolute private host paths and arbitrary model/check output must not be published. Evidence needs a protected ownership-bound store and verifiable content references; signatures or an equivalently qualified trusted transport must prevent substituted receipts. This stage does not implement that production store or receipt authenticator.
